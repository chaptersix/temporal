# WI-017 — Local load, state growth and migration boundary

Status: draft specification; implementation depends on accepted WI-015/M3.
Milestone: M4. No acceptance or benchmark results are claimed by this record.
Local workload planning can proceed while M3 compatibility work finishes.

## Goal and dependencies

Discharge P6.1–P6.4 with reproducible old-CHASM/scheduler2 comparisons using
actual local frontend, History, SQLite persistence, tasks and callbacks. Reuse
accepted functional backend selection and independent typed/persisted identity.
Do not substitute mock-node counters or finite-model throughput for physical
service evidence. Keep migration explicitly unsupported and default routing
unchanged; no rollout, push or remote workload is authorized.

## Workload specification before measurement

Hold schedule definitions, payload bytes, worker behavior, namespace settings,
local cluster topology and collection methods constant between backends and
between baseline/10x offered-load runs. Record exact source commit, seeds,
CPU/OS/toolchain, Go settings, database configuration and commands. Specify warmup,
measurement and drain periods in the executable workload artifact before running.
Use a fixed seeded arrival trace; report offered versus accepted versus completed
work separately. A closed-loop client that slows when the server slows does not
establish offered throughput or backlog growth.

Required workload families from the plan:

| Family | Controlled stimuli | Required observations |
| --- | --- | --- |
| Metadata reads | Describe/List/Count while schedules and large payloads remain fixed | API latency distribution, database reads, decoded nodes/bytes, CPU/memory |
| Due bursts | Identical interval phases across a fixed schedule population | Start latency from nominal/due time, throughput, queue age/backlog, per-transaction work |
| Large payload and backfill | Fixed valid action/result/failure sizes and accepted historical ranges | Serialized state/write bytes, retained payload ownership, node/task counts, drain/fairness |
| Long-lived tracked workflows | Gated children under tracked overlap policies | Live operation growth, metadata query cost, configured capacity, completion recovery |
| Callback storms | Release a known set of gated children together; explicitly count duplicate delivery if injected | Callback latency/throughput, lock contention, duplicate accounting, terminal retention |
| Sustained overload | Fixed offered ingress above measured service rate, followed by stop-and-drain | Accepted/rejected/skipped/dropped dispositions, peak backlog/resources, eventual recovery |

For each family define baseline offered arrival rate R, then10R with every other
input fixed. Choose R in a small documented calibration run and freeze it before
comparison; retain calibration failures and explain the choice. If a run reaches
an existing transport/state limit, record the rejection and retained-authority
outcome. Do not increase server limits to turn the same workload green. If a
workload cannot run at the requested rate on this host, report offered/achieved
rates and the limiting resource instead of calling it10x achieved throughput.

## Measurement and evidence contract

Measure wall-clock distributions (including p50/p95/p99 where sample size supports
them), total and successful throughput, backlog/time-to-drain, CPU and RSS, task
and DATA-node counts, transaction duration/contention, preparation/deserialization,
serialized/write bytes, persistence reads and restart cost. Attribute instrumentation
to its layer: service counters, database operations, serialized node bytes and host
process samples are different measurements. Report missing metrics explicitly and
supply instrumentation when required; logs alone cannot imply a physical cost.
Keep instrumentation local/test-only, bounded and identical across compared runs.

Use an actual shard close/reload at a specified accepted-work point to measure
restart cost and verify no loss/double start. Record the authority/dedup horizon,
terminal-record/payload retention and operator-visible recovery behavior. Preserve
the distinction between a bounded number of logical transitions and metadata work
that scales with active state, especially when MaxBufferSize disables a limit.
This distinction is an acceptance obligation, not a footnote that closes the gate.

## ADLC sequence and acceptance

1. Review workload definitions and instrumented layer mappings independently.
2. Implement the reusable local runner and prove its offered-rate/counter collection
   with focused harness checks and existing functional fixtures.
3. Run matched baseline and10x traces on both backends; retain raw observations,
   exact invocations, source/environment hashes and failure classifications.
4. Diagnose regressions or unbounded work/retention. Fix required behavior and repeat
   only affected comparisons with clearly separated source versions.
5. Produce a report linking measurements, benefits, costs, capacity recovery,
   retention/dedup tradeoffs, proof boundaries and unresolved risks.
6. Independent review audits all P6 requirements against artifacts, including the
   explicit unsupported migration boundary. M4 closes only when that audit passes.

The original checkout remains untouched. Evidence belongs under evidence/wi017;
large raw observations may be compressed losslessly with hashes. Results from
WI-015 correctness runs are reusable correctness evidence but are not performance
baseline measurements.
