# Scheduler2 typed visibility and metadata ports

The five CHASM-only scenario bodies were copied unchanged in assertions and stimuli to standalone scheduler2 tests. Only test entry point, explicit backend/context, root parallelization, and suite assertion receiver changed. Original cases remain intact; no skips or fallback. The dedicated scheduler2 frontend identifies the execution independently of the old CHASM experiment header.

Initial run failed the two typed visibility cases: ScheduleNextActionTime was unregistered (explicit invalid-query error), and the running-count query never matched. Memo replacement (including nil versus empty), large schedule ID starts, and preserving a schedule ID with the reserved V1 prefix passed. The fixed run passes all five cases.

The narrow source change registers DateTime01 for ScheduleNextActionTime and Int01/Int02 for ScheduleRunningWorkflowCount/ScheduleBufferedStartsCount, matching existing CHASM scheduler aliases and types. SearchAttributes reads the same first persisted future preview used by List; accepted transitions build that preview with the current configured SpecBuilder. It counts completion-tracked started operations only after the actual start RunID is known, matching Describe and legacy Invoker.runningWorkflowExecutions. Buffered count is the existing bounded queue plus unconfirmed starts, the same public buffer boundary as Describe. Zero counts are emitted explicitly, and closed schedules omit all three lifecycle attributes. The new unit test covers zero, admitted-but-unacknowledged, acknowledged running, completed, and closed states through the real component transition harness.

Evidence is local SQLite functional visibility indexing/querying, not a production routing or migration claim. This does not cover idle-close time indexing, physical shard reload, distributed visibility backends, or the remaining functional matrix. Parent retains those open rows. Parent owns final consolidated lint; these changes postdate the earlier checkpoint compilation. Exact commands and final source fingerprints are in manifest.json; initial, fixed, and unit logs are retained separately.
