# Remaining public contract audit

Read-only source audit after the unchanged 18-leaf contract suite passed (34.673s; `coordinator-progress/scheduler2-wi015-pump-contract03.log`). This is not M3 acceptance. Counterexamples below are source-derived next tests, not newly executed reproductions. No production or test files changed for this audit.

## Configured capacity is not implemented by admission

`internal/decision/buffer.go:32,77`, `decision.go:183`, and `manual.go:52,103,130` still impose queue/unfinished-operation capacity four. Public command ingress capacity 100 and the runtime-configured logical SKIP group do not change these admission limits. The existing CHASM generator instead obtains the live namespace `Tweakables.MaxBufferSize` and subtracts `len(invoker.BufferedStarts)` (`chasm/lib/scheduler/generator_tasks.go:91-96`); nonpositive values disable that generator limit, with an explicit test in `generator_tasks_test.go`.

Concrete tests required: hold a BUFFER_ALL workflow open and generate more than four waiting occurrences with configured capacity 1000; repeat with capacity one and zero. The current queue drops at four regardless. Hold four ALLOW_ALL start acknowledgments unresolved and deliver a fifth eligible automatic occurrence: `admit` increments CapacityDropped instead of preserving it, despite the much larger configured buffer. Check actual drops/counters and subsequent draining, not just ingress acceptance.

Next implementation choice: separate bounded transaction work from configured retained buffering and outstanding-operation scheduling. Map which new records represent old BufferedStarts exactly (unconfirmed starts versus queued candidates versus running tracked workflows); do not replace every four with MaxBufferSize indiscriminately. Carry explicit public capacity inputs into admission, retain the finite internal domain for existing models, and add public tests for live configuration reduction, disabled limits, overflow accounting, callback interleaving and fairness. Extending storage cardinality also requires reviewing whole-queue scans, operation-map scans and persisted summaries. The existing finite proofs do not establish this larger-domain refinement.

## Public timestamp acceptance exceeds the prototype execution domain

`occurrence.NewPublic` removes definition-size limits only. `supported` and `validCursor` still restrict execution to [2000,2101), plus the immediately preceding cursor; `Run`, `Update` and serialized-state validation enforce that domain. `AcceptBackfill` explicitly rejects any range outside it (`backfill.go:45-47`). `AcceptManual` separately rejects protobuf-valid timestamps not exactly representable as int64 Unix nanoseconds (`manual.go:49-52`). Frontend schedule/patch/matching validation instead uses protobuf `Timestamp.CheckValid` (`workflow_handler.go:7264-7277,7320-7354`).

Concrete tests required: interval backfill over a few seconds in 1999; manual trigger ScheduledTime in year 2500; protobuf-valid historical/future StartTime/EndTime and out-of-range no-match windows. The first two are rejected by scheduler2 after frontend acceptance. Constructor StartTime/EndTime alone are *not* rejected by validateBounds, so a test must inspect eventual behavior rather than assume Create returns an error.

Important legacy boundary: `CompiledSpec.GetNextTime` clamps to StartTime (nil means epoch) and terminates above maxCalendarYear=2100 (`service/worker/scheduler/spec.go:299-340`); structured calendars validate years 2000..2100. Therefore accepting a timestamp outside 2100 does not imply producing calendar occurrences there. Intervals before 2000 and accepting an empty future range remain distinct obligations. Public matching-times currently uses the legacy compiled spec directly (`public_mutation.go:213`), making pre-2000 matching versus rejected Backfill a useful same-definition consistency test.

Next implementation choice: use public time representation/normalization that preserves protobuf timestamps, explicitly map exhausted windows to legacy empty results, and retain the finite proof enumerator as a separately stated domain. Int64 nanosecond fields cannot represent the entire public timestamp domain; merely removing range guards risks overflow and wrong deterministic identities.

## Frontend validation and authorization: no demonstrated bypass

Create runs workflow ID/request ID, overlap, patch timestamps, canonicalization, time-skipping and start-workflow validation before the selected branch (`workflow_handler.go:3921-3993`). `createScheduleSelected` resolves namespace, validates search attributes and payload size before invoking the backend. Update and Patch similarly validate before the selected branch; matching validates timestamps. Generic authorization strips spoofed principal headers, authorizes the namespace/API request, and checks cross-namespace targets before calling the handler (`common/authorization/interceptor.go:159-187`). Selecting a backend inside that handler does not bypass those interceptors.

This source trace is not an exhaustive negative authorization test. Add actual frontend denial/no-write cases for Create/Update/Patch/Delete and read/list/count/matching; verify namespace isolation and spoofed-principal stripping, plus malformed policies/timestamps/start action/search attributes/payload size with unchanged durable state. Reuse shared frontend tests where they exercise the selected backend; do not infer failure from absence of a backend-specific authorizer. No source-backed authorization defect established in this audit.

## Closed/recreated physical fences: composition evidence still needed

`StartHandler` and `EffectHandler` merge external results with `chasm.NewComponentRef(ref.ExecutionKey)`, retaining the original run rather than resolving the current business ID (`tasks.go:80-86`, `effects_tasks.go:83`). Closed validation and incarnation checks fence results. `HandleNexusCompletion` relies on History validating the component reference before invoking it and then checks closed/operation/chain identity.

Existing evidence is meaningful but split: `lifecycle_test.go:40-99` saves actual physical envelopes, publishes close, reloads and rejects old side-effect envelopes; `physical_wake_test.go` checks physical delivery-time changes cannot replace logical wakes; public same-ID recreation (`tests/schedule2_public_test.go:246-252`) proves new conflict identity and old run remains closed. These are not a single History-backed close/recreate/deliver-old-envelope test.

Next test: retain actual pending Start/Effect/Work physical tasks and an in-flight acknowledgment/callback, close and recreate the same public business ID, then deliver each against its original exact run through the actual History dispatch path after reload. Assert zero external action for undispatched stale tasks, no new-run state/counter mutation from late results, and continued new-run progress. Include failed-close publication as the complementary case: the old run retains authority. No demonstrated source bug in exact-run fencing; remaining issue is end-to-end composition evidence, not permission to narrow the contract.
