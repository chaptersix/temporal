# Addressed operation retirement integration

This slice implements the keyed-operation adapter, without activating the keyed public runtime or migrating existing executions. Finite storage retains its existing retention scan. Public keyed storage uses the exact StartOnly predicate, admission trigger `OperationCount >= 4`, and minimum signed legacy Nominal then operation ID. Threshold4 remains a retention trigger, not an operation cap.

`operation_indexes.go` reconstructs each eligible operation identity from the same automatic/manual/backfill precedence as decision admission. Explicit timestamps are validated, the common execution incarnation and stored occurrence/action/full IDs must agree, and the fixed suffix constructor applies the proven73-byte generated-identity bound. Wide timestamps do not replace the legacy Nominal sort field.

`prepareOperationRecords` invokes capture-only `prepareOperationIndexes` after record/count preflight. The adapter uses the existing CountBatch over OperationPages, validates each old/new StartOnly identity, removes the old key and inserts the new key, then captures a detached complete mutation list. No DATA publication occurs during planning. Even unchanged StartOnly membership is deleted/reinserted in the overlay, detecting a missing addressed membership. The operation plan publishes index pages, addressed records and control in one enclosing CHASM transaction after all rejecting preflight. Framework panic requires discarding that transaction; no recovery can continue a partially published lease.

An actual `RetirementCount` scalar lives in OperationStoreControl. `CountBatch.RetirementCount` validates the owning root and its immediate children in at most8 counted reads. The adapter compares the index cardinality with the persisted scalar before planning/selection and with the prospective scalar after mutation. Missing owning root with positive scalar is an error; zero scalar plus absent root is valid. The scalar is nonnegative and no larger than OperationCount. Minimum selection then reads and validates the addressed operation, eligibility and reconstructed exact key. It never silently falls back to the legacy map scan.

Validation is local to touched paths, root cardinality and selected records. It is not a full audit of unrelated index subtrees or unrelated operation metadata. This matches the bounded hot-path contract; full cold/export auditing is a separate boundary.

## Work bounds

A record plan contains at most3 addressed changes. Each can remove and add one retirement key: at most6 fixed-width point mutations, plus two cardinality checks. From the reviewed primitive this is at most6*2820+16 =16936 counted index reads, plus3 addressed old-operation reads in this helper (record/request/blob preflight is separately bounded). Selection is one cardinality check plus minimum path plus one addressed operation: at most2828 counted index reads and one record read. The constants are conservative source ceilings, not typical measured work. The detached plan coalesces shared page changes through CountBatch before publication. Future readiness/running indexes can share OperationPages under separate owner/type namespaces.
